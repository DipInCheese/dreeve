---
title: "Multiple users"
description: "Run one Dreeve installation for as many people as you like, each with their own address, data and admin login."
---

One Dreeve installation can serve as many people as you like. Every user gets their own **address**
(e.g. `https://dreeve.example.com/alice`), **data** (database, photos, caches), **settings** and **admin login**.
Users never see each other's data.

You, the **owner**, have a dashboard like everyone else, plus a **Users** page in your admin panel to add,
invite, disable and remove users. New users get an **invite link** to pick their own password.

This page sets it up behind a [Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/),
so nothing on your network has to be opened up.

:::note
Replace `<github-user>` below with the GitHub account of the fork you use. The fork publishes its
image to `ghcr.io/<github-user>/dreeve:multi-user`.
:::

## Installation

You need a machine with Docker and a domain on Cloudflare.

```bash
mkdir dreeve && cd dreeve
curl -o docker-compose.yml https://raw.githubusercontent.com/<github-user>/dreeve/feature/multi-user/docker/multi-user/docker-compose.yml
curl -o .env https://raw.githubusercontent.com/<github-user>/dreeve/feature/multi-user/docker/multi-user/example.env
chmod 600 .env
nano .env
```

Fill in `.env`:

```dotenv title=".env"
DREEVE_IMAGE=ghcr.io/<github-user>/dreeve:multi-user
TZ=Europe/Brussels
TUNNEL_TOKEN=eyJh...
DREEVE_USER_URL=https://dreeve.example.com/{user}
DREEVE_OWNER=alice
```

Start it and read the logs:

```bash
docker compose up -d
docker compose logs app
```

The logs show a link like `https://dreeve.example.com/alice/invite/...`. Open it, pick your password and sign in
with username `alice`. You are now the owner.

## Cloudflare Tunnel

1. In the Cloudflare dashboard, go to **Zero Trust → Networks → Tunnels → Create a tunnel** and choose **Cloudflared**.
2. Copy the token (the long value after `--token`) into `TUNNEL_TOKEN` in `.env`. You can skip the install
   instructions, the tunnel already runs in the `cloudflared` container.
3. Add one **public hostname** for Dreeve. Cloudflare creates the DNS record for it:

   | Subdomain | Domain        | Service type | URL        |
   |-----------|---------------|--------------|------------|
   | `dreeve`  | `example.com` | HTTP         | `app:8080` |

Dreeve picks the user from the first part of the path: `https://dreeve.example.com/alice` is Alice,
`https://dreeve.example.com/bob` is Bob. Any other path gets a plain "Not found".

:::tip
Your Dreeve pages are reachable by anyone who knows the address. To limit who can open them, put a
[Cloudflare Access](https://developers.cloudflare.com/cloudflare-one/applications/configure-apps/self-hosted-apps/)
application in front of `dreeve.example.com`. Leave `/*/invite/*` open, or invited users can not pick their password.
:::

:::note[A subdomain per user]
`DREEVE_USER_URL=https://{user}.example.com` gives every user a subdomain instead (`alice.example.com`). That needs a
wildcard hostname (`*`) in the tunnel and a wildcard `CNAME` DNS record. Subdomains keep users apart in the browser as
well; with paths, all users share one browser origin (see [Security](#security)).
:::

## Managing users

Sign in, open your admin panel and go to **Users**:

* **Add user**: pick a name (lowercase letters, digits and dashes). It becomes part of the user's address and their
  username. Names Dreeve uses for its own pages, such as `admin`, `api` or `gear`, can not be used.
  You get an invite link to send to them.
* **New invite link**: when someone forgot their password, or did not use their link in time.
  Their old password keeps working until they pick a new one.
* **Disable / Enable**: blocks or unblocks a user. Their data is kept.
* **Remove**: the user's address stops working. Their data is not deleted but moved to `data/.removed/`.

Invite links work once, are valid for 7 days and are only shown when they are created.

The same is possible from the command line, which also helps when you are locked out yourself:

```bash
docker compose exec app bin/dreeve-users status
docker compose exec app bin/dreeve-users add bob
docker compose exec app bin/dreeve-users invite alice
```

## Settings per user

Settings in `.env` apply to every user. Most settings are made in each user's admin panel. For the few settings that
only exist as environment variables, a single user's values go in `data/<name>/.env`, for example their own AI key:

```dotenv title="data/alice/.env"
AI_API_KEY=...
```

Changes are picked up within a minute, no restart needed. `TZ`, `TRUSTED_PROXIES`, `PUID` and `PGID` apply to the
whole installation and can not be set per user.

## Security

* Passwords are picked by the users themselves through the invite link; nobody else ever sees them.
  They are stored as a hash in the user's data folder, readable by its owner only.
* Invite links are random 256-bit tokens. Only a hash of them is stored, they work once and expire after 7 days.
* After 5 failed sign-ins within 15 minutes, signing in is blocked for that username and IP address for a while.
* Every user gets a random `APP_SECRET`, generated on first start and stored in their data folder.
* Each user's data, caches and sessions are kept apart. A login for one user is not valid for another, and every
  user's session cookie is only sent to their own path.
* With an address per path, all users share one browser origin. Should Dreeve ever have a bug that lets someone
  inject a script into a page, that script could act on behalf of other users signed in in the same browser.
  With a subdomain per user, the browser keeps users fully apart. Only invite people you trust, or use subdomains.
* Only the owner can manage users; for everyone else the **Users** page does not exist.
* The `cloudflared` container only receives the tunnel token, and no ports are published on your machine.
* Garmin passwords are only passed on to log in and never stored. The Garmin session of each user is kept in their
  data folder, readable by its owner only. The `health-sync` service is only reachable by the app, with a secret
  generated on first start. See [Garmin Connect](/integrations/garmin-connect/).

## Data and backups

Everything lives in `./data`, one folder per user:

```text
data/
├── .users.json       <- the users and pending invites
├── .health-sync-secret <- lets the app talk to health-sync
├── alice/
│   ├── storage/      <- database, photos and files
│   ├── build/        <- render cache
│   ├── garmin/       <- Garmin session and sync progress
│   └── watch/        <- drop .fit/.tcx/.gpx files here to import them
├── bob/
└── .removed/         <- data of removed users
```

Back up `./data` and `.env`, and you have backed up everything.

## Updating

```bash
docker compose pull && docker compose up -d
```

Compare your `docker-compose.yml` with the latest one now and then: new services, like `health-sync` for
[Garmin Connect](/integrations/garmin-connect/), are only added by copying them over.

## Console commands

Console commands run for one user at a time, pick the user with `DREEVE_USER`:

```bash
docker compose exec -e DREEVE_USER=alice app bin/console app:import:files
```

## Logs

```bash
docker compose logs -f app
```

Each user's own logs are in `data/<name>/storage/files/logs/`.
